# 用户门店 NFC 绑定接口

用户在门店列表或品牌详情中打开“申请激活码牌”，输入分配给当前租户的六位编号。绑定只在码牌上写入 `store_id`，同一门店可绑定多个编号，不保存 `user_id`。用户只能操作自己的、尚未删除的门店。

## 接口

两个接口均继承 `BaseApiController`，需要用户登录。租户由现有中间件解析并由模型全局作用域自动过滤，控制器和业务方法不再传递租户参数或重复拼接 `tenant_id` 查询条件。客户端只提交门店 ID 和码牌编号，不提交用户身份。

- `POST /api/merchant.nfc_code/activate`：请求 `{ "store_id": 1, "code": "AB12C3" }`，成功返回 `{ "id": 10, "code": "AB12C3", "store_id": 1, "activated_at": 1794900000 }`。
- `GET /api/merchant.nfc_code/lists?store_id=1&page_no=1&page_size=10`：返回 `count`、`lists`、`page_no`、`page_size`。每项结构与激活响应相同，每页最多 100 条，按主键倒序。

编号去掉两端空白并转为大写后校验。码牌必须已分配给当前租户；同一编号再次提交到同一门店会返回原结果，不修改时间。已绑定其他门店的编号不能重新绑定。不可用码牌和无门店权限均返回现有的统一失败响应，前端保留输入并就地显示原因。

## 数据访问和事务

门店通过现有 `MerchantStore` 模型查询，保留软删除和项目原有租户表策略，业务层只增加门店 ID 及当前登录用户条件。NFC 库存由平台统一生成，始终保存在共享库存表；其全局作用域自动应用中间件确定的当前租户，查询编号、更新绑定和读取列表均沿用该作用域，业务层不重复加租户条件。缺少有效租户时无法访问库存。平台端既有行为保留，核心中间件和公共模型不变。

激活在模型连接的事务内锁定门店和码牌，再对 `store_id IS NULL` 的当前记录执行条件更新。重复请求不会新增记录，竞争同一编号时只有第一个门店能成功。列表每次先校验门店归属，不能通过输入其他门店 ID 读取记录。

复用已有 `update_time` 存储本次绑定时刻，接口将它命名为 `activated_at` 供现有弹窗展示；它是响应字段，不是新增数据库列。重复激活不会更新时间。现阶段没有解绑或重新绑定操作。

## 验证与发布

本次不增加数据库字段，也不需要执行新 SQL。部署服务端及配套 PC 前端后，原门店弹窗的列表和激活请求即可使用。

启用 `pdo_sqlite` 后运行 `php tests/nfc-code/store-binding.php`。测试只使用内存数据，覆盖本人门店、同店多码、重复请求、不可用码牌、已删除门店、分页和门店主键重复时的租户限制；同一入口同时回归此前的平台生成与分配功能。真实 MySQL 行锁竞争仍需部署后联调。
